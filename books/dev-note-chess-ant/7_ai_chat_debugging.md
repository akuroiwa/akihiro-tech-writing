---

`py-chessboardjs` の開発が始まった2023年末、私はフロントエンドの JavaScript とバックエンドの Python のつなぎ込みにおいて、無数のエラーとバグの嵐に遭遇していました。

この時、デバッグの強力な壁打ち相手となってくれたのが、ChatGPT と当時の Google Bard でした。

---

## `chess_ant.main()` 呼び出しエラーとの遭遇

2023年11月29日、`py-chessboardjs` のコミットログに以下のようなメッセージが記録されています。

* **Commit Message**: `What should I do about the error in chess_ant.main()?`

これは、JavaScript 側から Python 側の `chess-ant` 探索プログラムのエントリポイントを呼び出そうとした際に発生した重大なインポートエラーや引数の不整合に関する格闘の記録です。

当時はまだ、現在の `antigravity-cli` のように、AIエージェントがワークスペースのファイル関係を俯瞰し、自動でエラー原因を解析してくれるようなスマートな環境はありませんでした。

ブラウザで ChatGPT と Bard をそれぞれ開き、コンソールに吐き出されたトレースバックやエラーメッセージをコピペし、「この Python スクリプトを外部からインポートしてメイン関数を呼び出したいのですが、何が原因でしょうか？」と質問し、AIが生成した推測コードを手動で修正してはファイルを保存し、ターミナルで `python start.py` を手動起動する、というきわめて泥臭い対話デバッグでした。

---

## JavaScript と Python の指し手同期のズレ

また、探索エンジン単体のエラーだけでなく、GUI 独自の表示バグやイベントハンドラの競合にも悩まされました。

特に、チェス盤の「キャスリング（キングとルークの特殊な移動）」処理や、過去の対局履歴を示す PGN (Portable Game Notation) ファイルの読み込みにおいて、`chess.js` の状態更新と `chessboard.js` のイベント発火、さらに `pywebview` を介した Python 側の処理が互いに干渉し、同期が崩れるバグが発生しました。

また、`chessboard.js` は、キャスリング等の特定動作時に状態遷移が複数回発生する仕様になっていました。そのイベントを誤操作と解釈しないよう、ロックフラグを用いて処理を制御する設計を施す必要がありました。

```javascript
// 当時の応急処置：キャスリング時など、JS側の描画完了を待ってからコンピュータの思考を走らせるための setTimeout 調整
if (lastMove === 'O-O' || lastMove === 'O-O-O') {
    isCastlingInProgress = true;
} else {
    // コンピュータの手を即座に実行すると描画がバグるため遅延を挟む（当時の応急処置）
    window.setTimeout(makeComputerMove, 250);
}
```

「キャスリングを行うと盤面の描画がフリーズする」「PGNをロードした時に指し手履歴が空になってしまう」といった、UIの挙動に関するバグを解決するため、AIに「キャスリングの挙動とイベントハンドラの競合を防ぐ最適な遅延処理はどう書くべきか」を相談しました。

ChatGPT や Bard が提示した `setTimeout` による処理の遅延や、イベントロックフラグ（`isCastlingInProgress`）の導入といったアドバイスを得て、JSとPythonという異なる言語間の連携バグを一つ一つクリアしていきました。

しかし、これらの「指し手の遅延調整」は、一時的な応急処置に過ぎませんでした。2年後、アプリケーションがより重い探索エンジンと本格的に並行稼働し始めたとき、この非同期設計は致命的なフリーズ問題として再び牙をむくことになります。
