title: "第3章：fpocket-snap における自動テスト・リリース (CI/CD) の失敗談"
---

`spec-craft` による仕様駆動開発のプロセスは、ソフトウェアのコード記述だけでなく、そのパッケージングや配布、すなわち CI/CD（継続的インテグレーション/継続的デリバリー）の自動化領域へも拡張されました。

その最も過酷な実験場となったのが、タンパク質の結合部位予測ツール [`fpocket`](https://github.com/Discngine/fpocket) を Snap パッケージとして自動配布する [**`fpocket-snap`**](https://github.com/akuroiwa/fpocket-snap) プロジェクトでした。

---

## Snapcraft パッケージングの罠

Linux アプリケーションをあらゆるディストリビューションで動作可能にするパッケージ規格「Snap」は強力ですが、その作成ツールである `Snapcraft` の設定と動作環境の制限は、きわめて複雑です。

特に、Snap パッケージが実行時に隔離されたサンドボックス環境で動作する関係上、
- 必要なライブラリや動的リンクの依存関係をどのようにパッケージ内に封入（ステージング）するか。
- システムの他のパーツ（ネットワークやローカルファイル）にアクセスするためのインターフェース設定（Plugs and Slots）をどう定義するか。

これらの設計判断は、設定ミスが即座に起動エラーに繋がるため、注意深く進める必要があるプロセスでした。

---

## GitHub Actions との連携失敗

さらに、このパッケージビルドを GitHub へのプッシュと同時に自動化するための **GitHub Actions** ワークフロー構築において、私たちは数多くの失敗を繰り返しました。

ローカル環境では正常にビルド・動作していた Snap パッケージが、GitHub 側のクリーンな VM（仮想マシン）環境に移行した途端、依存するライブラリの不足やアーキテクチャの違いによってビルドエラーを多発させたのです。

また、自動ビルドしたパッケージを Snap ストアへ自動リリースするための API トークン（認証キー）の設定や、Trusted Publishing の連携ミスにより、リリースが却下されるトラブルにも見舞われました。

一時期は、GitHub Actions のログにエラーが多発し、何が原因で VM 内の Snapcraft が停止しているのか、ログだけでは判別が難しい状態に陥りました。

---

## CI/CD 構築における AI エージェントの活用

この難度の高い CI/CD デバッグにおいて、仕様駆動開発（specs）に基づいた AI エージェントとの連携が有効に機能しました。

私たちは「GitHub Actions での Snapcraft ビルドエラーの解消」という明確な境界を持つ仕様タスクを切り出し、AI エージェントに割り当てました。エージェントはビルドエラーのログをトレースし、
- VM環境内で必要となる前提パッケージ（`multipass` や `lxd` 等の仮想化ツール）のセットアップ手順の欠落。
- `snapcraft.yaml` におけるライブラリステージングパスの記述ミス。

などを一つずつ正確に突き止め、修正パッチを適用していきました。

手作業では多くの時間を費やす「Actions のログ監視と yaml 設定ファイルの修正ループ」について、仕様を明確に定義してエージェントにデバッグを指示することで、エラー原因の特定がスムーズに行え、ビルド成功へと繋げることができました。
