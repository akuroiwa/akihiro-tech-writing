本章では、チェス問題解決エンジン `chess-ant` プロジェクトの極初期である2019年から2020年にかけての試行錯誤を振り返ります。当時はまだAIアシスタントも存在せず、手元での完全な手作業（ソロ開発）と孤独な格闘の時代でした。

---

## 始まりは「人工アリ問題」 (Artificial Ant problem)

2019年5月28日。私のローカル開発環境のターミナルで、あるコピーコマンドが実行されました。

```bash
akuroiwa@akuroiwa-FMVA42CWY:~/文書/develop/git$ cp DEAP/deap/examples/gp/ant.py chess/sim-chess/src/
```

このコマンドこそが、後に続く5年間の長い旅路の最初の一歩でした。当時はまだ `chess-ant` という名前ではなく、**`sim-chess`** というプロジェクト名で開発をスタートさせていました。

このプロジェクトの出発点は、Pythonの進化計算 (Evolutionary Computation) ライブラリである `DEAP` のサンプルコードに収録されていた **「人工アリ問題」 (Artificial Ant problem)** でした。

遺伝的プログラミング (Genetic Programming: GP) の有名なベンチマークであるこのシミュレーションに触れた際、私の頭の中に一つの強烈な問いが浮かびました。

> **「人工アリ問題 (Artificial Ant problem) は、モンテカルロ木探索 (Monte Carlo Tree Search: MCTS) の代わりになり得るか？」**

チェスのような複雑なゲーム木を持つゲーム盤面において、アリが餌（最適な手）を探索するように、進化計算アルゴリズムを用いてチェスのルールや最善手を学習・探索させることができるのではないか。この仮説がすべての発端でした。

---

## 再帰関数に代わる「ラムダ計算」 (Lambda calculus) の実験

一般的なミニマックス法 (Minimax method) やアルファベータ枝切り (Alpha-Beta pruning) を用いた探索は、プログラム内部で再帰呼び出し (Recursive call) を用いてバックトラッキングを行うのが普通です。

しかし、私は「アリの探索行動」をベースにしたGP（遺伝的プログラミング）の表現力を用いて、再帰探索の代わりとして **ラムダ計算 (Lambda calculus)** を取り入れられないかと実験を始めました。
GPを用いてラムダ計算を行わせ、それが自動的に再帰関数のような探索木を構築・評価するロジックとして機能するかどうかを検証したのです。

極初期のソースコードが残る `dev-source/sim-chess/src/` の中には、その試行錯誤の残骸である `chess_ant_lambda.py` や `chess_ant_gp.py` などのファイルが残されています。
結論から言うと、この試みは**その多くが失敗作**に終わりました。しかし、この「再帰の代わりにGPで木探索の調整を行う」というアプローチへのこだわりが、後の `chess-ant` 独自のUCTアルゴリズム調整ロジックへと繋がっていくことになります。

## 初期の失敗：パッケージ管理とバージョン管理の欠如

今にして思えば、開発初期の最大の失敗は **「Gitによるバージョン管理を行っていなかったこと」** と **「明確なパッケージ管理（ビルド・デプロイ設計）をしていなかったこと」** です。

当時は、オープンソースのチェスGUIプラットフォームである `FlaskChess` を、自分のロジックの動作検証用GUIとして借用していました。手っ取り早くGUIで動かしてみたいという焦りから、探索エンジンのロジックを直接 `FlaskChess` のコード内部に埋め込んで開発を進めてしまっていたのです。

後にロジック部分を切り分けて `sim-chess/` として独立させたものの、構成やディレクトリ構造は現在と全く異なり、適切な履歴が残されませんでした。そのため、2019年から2020年にかけての多くのアイデアや、山のような失敗コードの正確な記録は、今や復元することができません。

個人開発において、**「どんなに小さく汚いコードであっても、最初からリポジトリを作成してコミットログを残しておくべきだった」** というのは、身に染みた最初の教訓です。

---

## パッケージコマンドと直接起動の二重生活

開発中の試行錯誤では、コードを修正するたびにいちいち `setup.py` を経由してパッケージをビルド（`pip install`）していては、開発のテンポが著しく損なわれます。

そのため、開発現場では常に二重の運用を行っていました。
基本的には、ディレクトリ内のファイルを直接呼び出す手法（例： `python chess_ant.py` や `python similarity_mcts.py` にオプションを付与して起動）でデバッグを行い、動作が安定した段階で初めてパッケージングを行い、コマンド（`similarity-mcts` 等）として呼び出せるかを確認する、という流れです。

AIエージェントが直接ファイルを書き換えて実行してくれる現在（2026年）の開発環境とは異なり、テキストエディタでコードを書き換え、手動でコマンドを実行してはプリントデバッグを繰り返すという、きわめて泥臭いサイクルを繰り返していました。

## MCTS (モンテカルロ木探索) へのシフトとC値の調整

GPによる探索制御の限界を感じる中で、チェスAIの技術トレンド（特にAlphaZeroのPUCTアルゴリズムなど）に刺激を受け、私は **モンテカルロ木探索 (Monte Carlo Tree Search: MCTS)** の導入へと大きく舵を切ることになります。

MCTSを導入するにあたり、最も重要な問題となったのが **探索と活用のバランスを制御する定数 $C$ (Exploration constant) の調整** でした。

この調整の重要性に気づかされたのは、有名な将棋AI開発者である山岡忠夫氏のブログ「TadaoYamaokaの開発日記」の以下の記事を読み込んでいた時のことです。

* [TadaoYamaokaの開発日記 - MCTSのCの調整](https://tadaoyamaoka.hatenablog.com/entry/2018/12/08/191619)

定数 $C$ の値の置き方ひとつで、エンジンが「まだ探索していない未知の手」を積極的に掘り下げるか、「すでに評価が高い手」を堅実に掘り下げるかがガラリと変わります。
ここで私は、初期の「人工アリ問題×GP」のアイデアを応用することを思いつきました。定数 $C$ を固定値とするのではなく、**「GP (遺伝的プログラミング) を用いて、盤面の状況（王手がかかっているか、探索深さはどうか等）に応じて最適な探索定数 $C$ を動的に選択させる」** という `chess-ant` 独自のUCT式（Upper Confidence Bound applied to Trees）のアーキテクチャが、この時に固まったのです。

```python
# chess-ant独自のUCT選択処理のイメージ
# GPによって生成された木構造（C_gp）が、状況に応じて 1/√1 から 1/√9 までの定数を出力する
a_t = arg_max(Q(s_t, a) + C_gp * math.sqrt(2 * math.log(N(s_t)) / N(s_t, a)))
```

こうして、2020年頃には `FlaskChess` に自前のMCTS探索エンジン `chess_mcts.py` を埋め込んだプロトタイプが動作し始め、後の本格的な Git 管理リポジトリである `chess-ant` 誕生への準備が整っていきました。

## コロナ禍と化学情報学 (Cheminformatics) への応用

2020年に入ると、世界は新型コロナウイルス感染症 (COVID-19) の世界的大流行という未曾有の事態に見舞われました。

毎日ニュースで報じられるウイルスの構造や治療薬候補の探索に関する話題を目にする中で、私はふと考えました。
> **「`chess-ant` の探索アルゴリズム（MCTSと遺伝的プログラミングの融合）は、ゲームだけでなく、新しい分子の探索や設計にも応用できるのではないか？」**

チェスの「駒の動きを選択して王手を目指す」プロセスは、化学における「原子や官能基を結合させて、目的の性質を持つ分子を設計する」プロセスと、木探索の観点から見れば非常によく似ています。

後に `chem-ant` や `chem-classification` といった、化学情報学 (Cheminformatics) 領域のパッケージ群を開発することになる強いモチベーションは、このコロナ禍という社会的背景から生まれたものでした。
